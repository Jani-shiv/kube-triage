# Rule Reference (KT-001 to KT-015)

Complete reference for all 15 built-in deterministic failure patterns. Rules are evaluated in priority order; first match wins.

## Rule Matching Logic

- Rules evaluated in order (KT-001 to KT-015)
- First match wins (highest priority)
- Each rule can match: container state, events, resource status, node conditions
- Templates use Go template syntax with context variables
- Remediation commands support template substitution

## Detailed Rule Specifications

### KT-001: OOMKilled Container Termination (CRITICAL)

**Category:** Resource  
**Trigger:** containerState.terminated.exitCode=137, reason=OOMKilled  
**Template Variables:** {ContainerName, LimitMemory, DeploymentName, Namespace, RestartCount}

**Diagnosis Template:**
```
Container {{ .ContainerName }} exceeded its hard memory limit of {{ .LimitMemory }}.
Kubernetes sent SIGKILL (exit code 137) to terminate the process.
```

**Remediation:**
1. Increase memory limit in deployment spec
2. Add memory request for QoS guarantees

**Prevention:**
- Set memory requests = limits for Guaranteed QoS class
- Configure Prometheus alerts: container_memory_usage_bytes > 0.8 * limit
- Profile application with pprof to identify memory leaks
- Implement graceful degradation under memory pressure

### KT-002: CrashLoopBackOff (HIGH)

**Category:** Lifecycle  
**Trigger:** containerState.waiting.reason=CrashLoopBackOff  
**Template Variables:** {ContainerName, RestartCount, PodName, Namespace}

**Diagnosis Template:**
```
Container {{ .ContainerName }} is in CrashLoopBackOff with {{ .RestartCount }} restarts.
The container fails repeatedly on startup. Check previous logs for the actual error.
```

**Remediation:**
1. Check previous container logs for root cause
2. Describe pod for events and configuration

**Prevention:**
- Configure proper liveness and readiness probes with appropriate initialDelaySeconds
- Set startup probes for slow-starting applications
- Ensure application handles SIGTERM gracefully
- Use init containers for pre-start dependencies

### KT-003: ImagePullBackOff / ErrImagePull (HIGH)

**Category:** Image  
**Trigger:** containerState.waiting.reason=ImagePullBackOff/ErrImagePull  
**Template Variables:** {ContainerName, Image, PodName, Namespace}

**Diagnosis Template:**
```
Kubernetes cannot pull the container image {{ .Image }}.
Common causes: wrong image name/tag, missing credentials, registry unreachable, rate limiting.
```

**Remediation:**
1. Verify image name and tag in pod spec
2. Check image pull secrets
3. Test image pull manually

### KT-015: Container Exited with Code 143 (SIGTERM) (LOW)

**Category:** Lifecycle  
**Trigger:** terminated.exitCode=143

**Diagnosis Template:**
```
Container {{ .ContainerName }} received SIGTERM (exit 143) and terminated gracefully.
This is normal during pod deletion, scaling down, or node drain.
```

**Remediation:** Normal termination - no action needed unless unexpected.

**Prevention:**
- Implement graceful shutdown handling (catch SIGTERM)
- Set appropriate terminationGracePeriodSeconds
- Use preStop hooks for cleanup

## Extending Rules

Rules are defined in `configs/heuristic-rules.yaml`. To add custom rules:

```yaml
rules:
  - id: "CUSTOM-001"
    name: "Custom Rule Name"
    category: "custom"
    severity: "HIGH"
    trigger:
      event:
        reason: ["CustomReason"]
    diagnosisTemplate: |
      Custom diagnosis for {{ .PodName }}
    remediationSteps:
      - type: "command"
        description: "Custom remediation"
        snippet: "kubectl custom-command {{ .PodName }}"
    prevention:
      - "Custom prevention tip"
```
